# Playify VPS audit — 6 September 2026

Target: `david@95.217.20.12`, deployment `/var/playify/app`, Git HEAD observed `f5ee863`. Read-only checks performed over SSH and HTTPS. No production code, configuration, or database records changed during the audit. SSH key installation was performed separately by the user to enable access.

## High-priority findings

These authorization findings are confirmed from deployed source, not by exploiting production accounts or changing records.

1. **Critical: registration accepts privileged roles.** `vps/api/src/routes/auth.ts:84` sets `userRole = role ?? 'fan'` from public registration input and stores it in both `User` and `profiles`. `src/lib/supabase.ts:36` grants administrative access based on that profile role. Enforce a server-selected registration role; require a privileged workflow for elevated roles.
2. **High: claim approval/rejection lacks administrative authorization.** `src/routes/claims.ts:7` and `:30` accept the authenticated user as reviewer without checking their role. The global admin middleware applies to `/v1/admin/*`, not these handlers. Apply explicit reviewer authorization to both operations.
3. **High: WebSocket channel authorization is missing.** `src/index.ts:228` accepts channel subscriptions without validating a signature, JWT, or channel membership. At line 245, client events can target channels without checking membership. Private messages and events may be exposed or spoofed if routed through this server. Validate subscriptions and restrict client events. Port 3443 is reachable externally. No private channel was joined during this audit.
4. **High: weak password recovery.** `src/routes/auth.ts:527` permits password reset using email and date of birth alone. The OTP branch marks `used_at` at line 538 but its lookup does not exclude already-used codes, allowing reuse within expiry. Require a secure, single-use recovery token and atomically consume it.
5. **High: payment callback does not reliably authenticate the sender.** `src/routes/mpesa.ts:36` only checks a shortcode when the caller includes it, then changes order status based on supplied callback fields. Validate payment status against the provider and enforce idempotent transitions before fulfillment. No payment request was submitted.
6. **High: API runs as root and its environment file is world-readable.** Observed Bun process owner is root; `/var/playify/app/vps/api/.env` has mode `0644`. Run the API as a dedicated unprivileged account and restrict secrets-file permissions. Secret values were not printed.

## Functional and deployment findings

- Public HTTPS checks passed for health, feed, trending, news, communities, sports, nearby with coordinates, and all seven named match-list endpoints tested: live, today, upcoming, results, standings, all, leagues. Some lists are empty; HTTP success does not establish data freshness.
- Anonymous requests to `/v1/admin/stats` and representative protected route prefixes returned 401. This proves an anonymous authentication gate, not correct authorization for every user role or handler.
- `/admin/` returns the same Flutter bootstrap HTML as `/`; the observed Nginx configuration has no separate React admin mapping. No separate admin build was found in the inspected web roots. A Flutter-internal admin screen, if present, was not exercised.
- The separate React admin source uses Supabase sessions and direct Supabase table operations, while the VPS API uses local PostgreSQL. Its root component checks session presence only. Deployment and authorization need reconciliation; Supabase policies were not queried.
- `/health/version` advertises 1.2.0/code 4 and `/app/playify.apk`; `/v1/app/version` advertises 1.2.1/code 5 and `/downloads/playify.apk`. The legacy APK URL returns HTML, while the current URL returns a 54,108,096-byte binary. Consolidate version metadata and repair the old URL.
- Environment-file checks found FCM credentials, M-Pesa consumer key/passkey, and both supported AI-provider keys missing/empty. Those integrations are not configured in this file; process-level overrides were not inspected. Resend email and MinIO configuration are present; delivery, uploads, and provider authentication were not exercised.
- The admin role helper also authorizes `official`, `organization`, and `moderator`. Confirm that these roles should receive the same broad administrative permissions.
- Probed `/v1/social/polls`, `/predictions`, and `/posts` GET collection paths returned 404; deployed routes use other read paths and/or POST methods. These are not established defects. `/v1/matches` without a subpath returned 401; actual list routes passed. Nearby without coordinates returned 400 as expected.

## VPS and database health

- Uptime about 10 days; load average 0.15 / 0.14 / 0.10 at initial observation.
- Root disk: 38 GB, 15% used. RAM: 3,814 MB total, about 3,127 MB available. No swap.
- No failed systemd units. Nginx, PostgreSQL, SSH, and Fail2Ban running.
- PostgreSQL 18.6, database `playify`, size 12 MB, 73 public tables.
- Database metadata checked using the application's credentials with `default_transaction_read_only=on` and a 10-second statement timeout.
- Application database role is not superuser, cannot create roles/databases, and has no BYPASSRLS attribute.
- No invalid indexes, unvalidated constraints, or sessions waiting on locks observed. These are metadata checks, not an exhaustive integrity verification.
- PostgreSQL listens on loopback. API/MinIO have wildcard listeners, but external connection attempts to ports 3000, 9000, and 9001 timed out from the audit computer. This does not prove firewall policy. Port 3443 was reachable.
- HTTPS certificate validation passed; TLS 1.3 negotiated; observed certificate expiry 25 November 2026.
- No database backups found in `/var/backups`, no user crontab for `david`, and no obvious database backup job among `/etc/cron.d` filenames. Root crontab, provider snapshots, offsite storage, and restore capability remain unverified.
- Inspected `api-error.log` was empty; 316 lines in `api.log` contained none of the checked common error markers. Other process logs and privileged logs were not inspected.

## Coverage and limitations

Inventoried 160 router handler declarations across 16 route files, plus inspected global routing and inline endpoints. Read representative sensitive handlers and ran over 30 HTTP requests against public/anonymous paths; this is not an end-to-end test of all functions.

No account creation, login attempts with user passwords, password resets, data mutations, uploads, notification sends, payment initiation, or account impersonation were performed. Authenticated admin workflows, Flutter UI behavior, third-party service operations, backup restoration, root-owned process configuration, firewall rules, and Supabase RLS remain unverified. Passwordless sudo is unavailable. Findings above should be fixed and then validated with dedicated test accounts before declaring the application fully functional.
